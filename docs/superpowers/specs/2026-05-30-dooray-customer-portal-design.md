# Dooray 고객사 업무요청 포털 설계

## 목표

Dooray 손님 계정 추가 정책 변경으로 인해, 고객사가 직접 Dooray에 접속하지 않고도 업무 요청, 진행 상태 확인, 댓글 작성, 첨부파일 등록을 할 수 있는 별도 고객 포털을 구축한다.

운영팀은 기존처럼 Dooray만 사용하고, 고객사는 고객 전용 사이트만 사용한다.

## 범위

1차 버전 범위는 아래로 한정한다.

- 고객사 사용자 로그인
- 고객사별 전용 Dooray 프로젝트 조회
- 칸반 보드 기반 업무 목록 조회
- 업무 상세 조회
- 신규 업무 등록
- 업무 상태 변경
- 댓글 등록 및 조회
- 첨부파일 등록 및 조회

아래는 1차 버전 범위에서 제외한다.

- 별도 업무 데이터베이스에 업무/댓글/첨부 저장
- 고객사 간 프로젝트 공유
- 고급 통계, 검색 인덱스, 감사 로그, SLA 대시보드
- 운영팀용 별도 관리자 화면

## 핵심 원칙

- Dooray를 유일한 업무 원본 시스템으로 사용한다.
- 고객 포털은 Dooray를 읽고 쓰는 얇은 전용 UI로 구성한다.
- 업무/댓글/첨부는 우리 서비스 DB에 저장하지 않는다.
- 고객사마다 Dooray 프로젝트를 분리한다.
- 고객사는 자기 회사에 연결된 Dooray 프로젝트만 접근할 수 있다.
- Supabase는 인증과 고객사-프로젝트 매핑 같은 최소 설정 데이터만 저장한다.

## 아키텍처

구성 요소는 아래와 같다.

- `Supabase Auth`: 고객 로그인 처리
- `Supabase Postgres`: 고객사, 멤버십, Dooray 프로젝트 매핑 저장
- `Frontend`: 고객 전용 포털 UI
- `Backend API`: 인증 확인 후 Dooray API 프록시 역할 수행
- `Dooray API`: 업무, 댓글, 첨부, 상태 변경의 실제 원본 시스템

Supabase에는 아래 최소 테이블만 둔다.

- `companies`
- `company_members`
- `company_dooray_projects`

흐름은 아래와 같다.

1. 고객이 포털에 로그인한다.
2. 서버는 로그인 사용자 정보를 확인한다.
3. 서버는 Supabase에서 해당 고객사에 매핑된 Dooray 프로젝트 ID를 찾는다.
4. 업무 목록/상세/댓글/첨부/상태 변경 요청은 모두 서버를 통해 Dooray API로 전달한다.
5. 응답 결과를 고객 화면에 그대로 반영한다.

## 고객사 식별 방식

1차 버전에서는 업무 데이터는 저장하지 않지만, 고객사와 Dooray 프로젝트 연결을 위해 Supabase에 최소 매핑 데이터를 저장한다.

최소 구조는 아래와 같다.

- `companies`: 고객사 기본 정보
- `company_members`: Supabase 사용자와 고객사 연결
- `company_dooray_projects`: 고객사와 Dooray 프로젝트 연결

식별 흐름은 아래와 같다.

1. 사용자가 Supabase Auth로 로그인한다.
2. 서버가 `auth.uid()` 기준으로 `company_members`를 조회한다.
3. 해당 `company_id`로 `company_dooray_projects`를 조회한다.
4. 조회된 `dooray_project_id`로 Dooray API를 호출한다.

초기 버전은 한 고객사당 활성 Dooray 프로젝트 1개만 허용하는 것이 가장 단순하다.

## 화면 설계

### 로그인 화면

- Supabase Auth 기반 로그인
- 이메일/비밀번호 또는 매직링크 중 하나 선택 가능
- 1차 버전은 운영 단순화를 위해 매직링크 또는 관리자 생성 계정 방식을 우선 고려한다

### 칸반 보드 화면

- 고객사 프로젝트의 업무를 상태 컬럼별로 표시
- 컬럼 명은 Dooray 실제 상태명을 그대로 사용하는 것을 기본으로 한다
- 카드에는 제목, 작성일, 최근 수정일, 중요도 정도를 표시한다
- 카드 클릭 시 업무 상세로 이동한다

### 업무 상세 화면

- 제목
- 본문
- 현재 상태
- 작성일/수정일
- 댓글 목록
- 첨부파일 목록
- 상태 변경 UI
- 댓글 작성 UI
- 첨부 업로드 UI

### 업무 등록 화면

- 제목
- 본문
- 우선순위 또는 분류가 필요하면 선택값 추가
- 파일 첨부
- 등록 즉시 Dooray 업무 생성

## 권한 규칙

- 로그인한 고객은 자기 고객사에 매핑된 Dooray 프로젝트만 조회 가능
- 다른 고객사의 Dooray 프로젝트 ID가 있더라도 직접 접근할 수 없어야 한다
- 업무 생성은 자기 프로젝트에만 가능
- 업무 상태 변경은 자기 프로젝트 업무에만 가능
- 댓글/첨부 등록도 자기 프로젝트 업무에만 가능

서버는 프론트에서 전달한 프로젝트 ID를 신뢰하지 않고, 로그인 사용자 기준으로 Supabase에서 프로젝트를 다시 계산해야 한다.

## 상태 처리 원칙

- 상태는 Dooray 상태를 그대로 사용한다
- 별도의 내부 상태 테이블이나 매핑 DB는 두지 않는다
- 고객 화면의 칸반 컬럼도 Dooray 상태명을 기반으로 표시한다
- 상태 변경 시 우리 서비스는 즉시 Dooray API를 호출하고 결과를 다시 조회해 화면을 갱신한다

이 방식은 단순하지만, Dooray 워크플로우 변경 시 고객 화면도 함께 영향을 받는다. 1차 버전에서는 단순성을 우선한다.

## 댓글 처리 원칙

- 고객 댓글은 저장 없이 Dooray 댓글로 바로 등록한다
- 상세 화면 진입 시 Dooray 댓글 목록을 실시간 조회한다
- 댓글 작성자 표시는 Dooray 응답 형식에 맞춘다

운영팀이 Dooray에서 단 댓글도 고객 화면에 그대로 노출된다.

## 첨부파일 처리 원칙

- 첨부파일도 우리 업무 DB에 저장하지 않는다
- 가능하면 업로드 즉시 Dooray 첨부 흐름에 맞춰 등록한다
- 상세 화면에서는 Dooray에 연결된 첨부파일 목록을 실시간 조회한다

첨부 업로드 API 구조가 복잡하거나 중간 저장소가 필요하면, 1차 버전에서만 임시 파일 저장을 허용할 수 있다. 다만 업무 메타데이터를 저장하는 별도 DB는 두지 않는다.

## 에러 처리

- Dooray API 실패 시 사용자에게 즉시 오류 메시지를 보여준다
- 생성/상태 변경/댓글/첨부 요청은 성공 여부를 명확히 표시한다
- 인증이 만료되면 재로그인을 유도한다
- 고객사 매핑이 없는 계정은 접근을 차단하고 안내 문구를 보여준다

## 테스트 전략

최소 검증 범위는 아래와 같다.

- 로그인 성공/실패
- 고객사별 프로젝트 분리 확인
- Supabase 고객사-프로젝트 매핑 조회
- 업무 목록 조회
- 업무 상세 조회
- 업무 생성
- 상태 변경
- 댓글 등록
- 첨부 등록
- 다른 고객사 프로젝트 접근 차단

기술 검증은 실제 개발 전에 Dooray API로 아래 PoC를 먼저 수행한다.

- 업무 1건 생성
- 업무 상태 1회 변경
- 댓글 1건 등록
- 첨부파일 1건 등록
- 업무/댓글/첨부 조회

## 장점

- 업무 데이터 이중화가 없다
- 동기화 복잡도가 낮다
- 운영팀은 기존 Dooray 운영 방식을 유지할 수 있다
- 고객사는 Dooray 계정 없이 전용 포털을 사용할 수 있다
- 초기 개발 범위를 최소화할 수 있다

## 제약과 후속 확장 포인트

- Supabase를 무료 플랜으로 시작할 수는 있지만, 운영 환경에서는 pause 정책과 성능 특성을 검토해야 한다
- Dooray API 응답 속도와 제한이 고객 UX에 직접 영향을 준다
- 검색, 통계, 히스토리, 알림 기능은 후속 버전에서 별도 저장소가 필요할 수 있다

후속 확장 시 가장 먼저 고려할 항목은 아래다.

- 고객사-프로젝트 매핑 관리 UI
- 캐시 계층
- 읽기 전용 검색 인덱스
- 알림 기능
- 최소 운영 로그 저장

## 추천 구현 방향

1차 버전은 아래 스택을 추천한다.

- Frontend: Next.js
- UI Starter: TailAdmin Next.js
- Auth: Supabase Auth
- Mapping DB: Supabase Postgres
- Backend: Next.js Route Handler 또는 별도 API 서버

권장 구현 방식은 `최소 매핑 DB + API 프록시 백엔드`다.

이 방식은 Dooray API 키를 서버에만 두고, 고객사별 프로젝트 접근 제어를 서버에서 일관되게 강제할 수 있다. 또한 고객사 추가 시 코드 수정 없이 매핑 정보만 갱신할 수 있다.

TailAdmin은 레이아웃, 네비게이션, 폼, 카드 같은 UI 스타터로만 사용하고, 데모 차트나 예제 데이터 구조는 그대로 따르지 않는다. 프로젝트 구조와 데이터 흐름은 이 설계 문서를 기준으로 유지한다.

## Supabase 최소 스키마

### companies

- `id`
- `name`
- `status`
- `created_at`

### company_members

- `id`
- `company_id`
- `user_id`
- `role`
- `created_at`

`user_id`는 Supabase Auth 사용자 ID와 연결한다.

### company_dooray_projects

- `id`
- `company_id`
- `dooray_project_id`
- `dooray_project_name`
- `active`
- `created_at`

## Supabase 접근 정책 원칙

- 로그인한 사용자는 자기 회사 정보만 조회 가능
- 로그인한 사용자는 자기 회사 멤버 정보만 조회 가능
- 로그인한 사용자는 자기 회사의 Dooray 프로젝트 매핑만 조회 가능
- 프로젝트 매핑 수정은 초기 버전에서 서버 또는 관리자만 수행
- Dooray API 호출은 반드시 서버에서만 처리

RLS는 `companies`, `company_members`, `company_dooray_projects` 세 테이블에만 적용하면 충분하다.
